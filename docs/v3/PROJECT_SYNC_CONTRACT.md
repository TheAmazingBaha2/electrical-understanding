# Future project synchronization contract

No transport/backend/account integration is enabled. `project-sync.js` defines a versioned envelope with project identity, authoritative revision/parent revision, device/mutation identity and a complete serializable project. It never reads/writes Supabase or lesson progress. Device pane/layout choices remain separate local preferences.

Three-way merge uses an explicitly known common base, never timestamp winner selection. Nonconflicting notes, metadata, additions and stable-ID snapshot edits can merge. Circuit, inventory, widget/instrument settings, measurements and experiment state merge as one atomic group to keep board state/compiled graph and instrument connections consistent. Concurrent different experiment edits are conservatively conflicts, not guessed topology merges. Snapshot deletion and a concurrent rename/change conflict on the stable snapshot ID. Tombstones preserve deletion identity; unknown approved metadata is retained. Original update times are recorded as merge evidence, not authority.

Any conflict preserves complete base/local/remote projects. An invalid merged contract also becomes a conflict. Future UI should present simple choices and recovery exports rather than a Git-style history. Never send graded answers or device layouts as project payload. Future backend must authorize owner access, compare revisions atomically, retain recovery copies, make mutation IDs idempotent and handle offline upload/download without silent overwrite. Costs/backend approval are required before enabling a transport; no cloud service was provisioned here.
